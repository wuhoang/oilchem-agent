# OilChem Agent 系统顶层设计

> 文档定位：顶层设计（High-Level Design）。
> 说明"系统要成为什么"（目标）、"分成哪些模块"（划分）、"每个模块怎么设计、实现哪些功能"（职责与功能）。
> 模块内部的类/接口/表结构等详细设计，见后续各模块的详细设计文档。
> 与 `docs/architecture.md` 的关系：该文档描述当前已实现代码的架构；本文描述目标态设计，演示版实现是它的子集。

---

## 1. 系统定位

**OilChem Agent 是"实验管理系统"与"实验硬件设备"之间的中间层。**

- 上游：实验管理系统（LIMS/ELN 类），是实验设计（Protocol）、人员、物料等信息的权威来源。
- 下游：自动实验设备、传感器、仪表（RS232 / USB / GPIB / 网络接口）。
- 核心价值：**人-机-料-数据 四者全程关联、可追溯**——哪个实验员、用哪台设备、消耗哪批物料/样品、按哪条方案、产出哪些数据点。
- 交互层（Web + Agent 对话）只是"顺带的门面"，不是系统主体。

---

## 2. 目标

### 2.1 演示版目标（PoC）

向三类用户展示一条**完整可跑的自动化实验主线**：

> 选择实验方案 → 一键开始实验 → 系统自动拆解步骤 → 设备逐步执行（备料→装样→升温→测量）→ 实时数据曲线 → 实验完成 → 全程追溯

- 三类用户视角各有落点：管理者（看板/大屏）、科学家（方案库/数据分析）、实验员（执行工作台）。
- 设备与管理系统均为 **Mock**（模拟设备状态机 + 预置实验方案），但**流程与数据模型是真实设计**，生产版直接复用。
- 演示链路稳定、可重复、有真实感数据（如 HTHP 失水仪漏失量曲线）。

### 2.2 生产版目标（生产可用）

- 对接真实实验管理系统：拉取实验设计、人员/物料主数据，回传实验结果。
- 对接真实自动实验设备：通过真实协议下发指令、采集数据，实现"设计→执行→数据"无人值守闭环。
- 自动实验：从管理系统拉取实验设计 → 中间层拆解编排 → 自动设备执行 → 数据采集入库 → 结果回传。
- 人-机-料-数据全程追溯，支撑合规审计与质量分析。
- LLM 仅承担交互层与辅助能力（方案文档解析、异常处置建议、报告生成），**不进入实验执行主链路**。

## 4. 模块设计

### M1 数据模型层（人-机-料-实验 追溯主数据）

**职责**：用关系型数据承载"谁-用什么-做哪个实验-产出什么"，是追溯能力的根基。

**核心实体与关联**：

```
experimenters（实验员）           devices（设备）
     │                                │
     │ 操作者                         │ 执行者
     ▼                                ▼
protocols（实验设计）──→ experiments（实验运行）──→ measurements（测量数据点）
     │                        │            │
     │ 步骤定义                 │ 使用        │ 关联
     ▼                        ▼            ▼
protocol_steps（步骤模板）   materials    samples
                            （物料主数据）  （样品实例）
```

**materials 与 samples 的区分（追溯维度不同）**：
- `materials`：**物料主数据**——配方成分/耗材的静态档案，如"某牌号膨润土""标准滤纸"，含规格、厂商、批次属性。
- `samples`：**样品实例**——实验中实际用到的"一份"物料或产物，含唯一编号、来源批次、当前状态（在用/留样/待处置）。
- 关系：一个 `material` 可产生多个 `sample`；一条实验记录"消耗/产出"的是具体的 `sample`，追溯"用了哪批物料"通过 sample → material 关联达成。
- 现有代码中 `samples` 表已存在，`materials` 为新增；`experiments` 关联 `sample_code` 引用具体样品。

**数据模型能力**：
- 核心：`protocols` / `protocol_steps` / `materials` / `measurements` 表；`experiments` 补上 `protocol_id`、`device_id`、`operator_id`、`sample_code` 关联字段；种子数据真实化（实验员、真实设备清单、2 条完整实验方案含步骤/参数/预期指标）。
- 增强（后续）：主数据（人员/物料/设备台账）与管理系统双向同步、数据版本化（方案修订、结果修订记录）。

### M2 编排引擎 ★ 技术核心

**职责**：把"一条实验方案"变成"一步步可执行、可跟踪、可异常处理的任务流"，并驱动设备完成。**引擎不感知设备真伪**——它只面向 M3 的设备抽象接口。

**核心设计**：
- **任务状态机**：`草稿 → 待执行 → 备料 → 执行中 → 数据采集 → 完成 / 异常 / 中止`
- **步骤队列**：方案拆解为有序步骤，每步携带：目标设备、动作、参数、超时、完成判据。
- **设备占用**：设备同时只服务一个实验步骤，冲突入队等待。
- **事件流**：实验进度/步骤状态/数据点通过 SSE 推送给前端与 Agent。
- **异常路径**：设备失败 → 标记异常 → 人工介入（重试/跳步/中止，均可恢复现场）。

**步骤模型（字段级）**——引擎消费的统一步骤结构：

```
ExperimentStep
  ├─ step_id / order            # 顺序号（来自 protocol_steps 展开）
  ├─ device_id                  # 目标设备（占用校验依据）
  ├─ action                     # 动作名：load_sample / set_temperature / hold /
  │                             #   measure / ramp / drain / report...
  ├─ params: {…}                # 动作参数，如 {temperature: 180, ramp_rate: 2}
  ├─ timeout_s                  # 本步超时（秒）
  ├─ complete_criteria          # 完成判据：{type: "target_reached"|"hold_duration"|"measurement_count", …}
  └─ status                     # pending / running / succeeded / failed / skipped
```

**步骤来源**：`POST /experiments/{id}/start` 时，引擎读取 `protocols` 关联的 `protocol_steps`（有序步骤模板），结合实验参数（如具体目标温度、样品编号）实例化为上述 `ExperimentStep` 列表，写入实验运行记录。演示版由预置方案直接提供步骤模板；生产版由 M4 从 LIMS 拉取方案导入。

**异常恢复策略**：
- 步骤失败 → 状态机进入 `异常`，引擎冻结现场（当前步骤参数、已完成步骤、已采数据点）。
- 人工介入的三个动作：**重试本步**（恢复现场后重新执行）、**跳过本步**（标记 skipped，继续后续）、**中止实验**（释放设备，保留已采集数据）。
- 恢复原则：现场不丢失——已完成的步骤、已写入的数据点、设备占用状态在介入期间保持可查询，不因异常回滚。

**能力分层**：
- 核心：步骤展开、状态机推进、设备占用、SSE 事件、数据点入库、异常冻结+人工介入。
- 增强（后续）：方案校验（参数合法性、物料库存、设备可用性预检）、步骤级超时/心跳自动中止卡死步骤、可选重试/降级策略。

### M3 设备驱动层

**职责**：统一屏蔽"设备长什么样"——对引擎暴露一致接口，真设备/模拟设备可互换。

**接口设计（驱动抽象）**：

```
DeviceDriver
  ├─ connect() / disconnect()
  ├─ execute_step(step) → 执行结果（成功/失败 + 状态码 + 错误信息）
  ├─ read_telemetry() → 实时读数（温度/压力/漏失量等，周期性拉取）
  ├─ get_status() → 设备状态（idle / busy / error / offline）
  └─ cancel() / abort()
```

**接口契约（引擎与驱动的约定）**：
- `execute_step` 是同步阻塞式的：引擎下发一步，驱动执行完成后才返回；引擎据此推进状态机。
- `read_telemetry` 与执行解耦：数据采集线程独立轮询，不阻塞步骤推进。
- 驱动层不感知实验语义——它只理解"动作 + 参数 + 完成判据"，不知道这步属于哪条实验。
- 异常以返回值表达（失败码 + 信息），不抛未捕获异常，保证引擎循环稳定。

**驱动实现**：
- `MockDriver`（演示版）：设备状态机 + **剧本化数据生成**，支撑演示与开发。
  - Mock 设备不再"随机漂移"，而是受编排引擎指挥：实验要求升温才升温、要求恒温才维持、要求测量才出点。
  - 剧本数据结构示例：`{action: "set_temperature", target: 180, ramp_rate: 2}` → 按爬坡速率逐 tick 逼近目标并上报遥测。
  - 预置设备型号行为库（如 HTHP 失水仪的行为参数），演示时直接实例化。
- `SerialDriver` / `HttpDriver` / `GpibDriver`（生产版）：真实协议，逐步替换 MockDriver，引擎与上层完全无感。

**能力分层**：
- 核心：统一驱动接口、MockDriver 剧本引擎、设备状态机。
- 增强（后续）：设备注册表、协议适配器、设备固件版本管理、连接健康检查。

### M4 管理系统对接层

**职责**：与实验管理系统之间的双向适配。

- 拉取：实验设计（Protocol）导入、人员/物料主数据同步。
- 回传：实验状态与结果数据上报。

**演示版功能**：预置方案即"Mock 源"（种子数据），接口形态先按生产版设计定义好。
**生产版功能**：REST 适配器（或文件/DB 直连适配器，取决于目标系统能力），增量同步、冲突处理。

### M5 交互层（Web 三视角 + Agent）

**职责**：让三类用户用各自的语言完成各自的事。Agent 对话与 Web 页面共享同一套后端 API 与事件流。

**Web 页面**：
- 实验看板（管理者）：设备状态、实验进度、人-机-料统计。
- 方案库 + 实验工作台（科学家/实验员）：浏览方案 → 开始实验 → 实时进度 + 数据曲线。
- 实验详情/追溯页（所有人）：单条实验的完整链条。

**Agent（基于现有 function calling 循环）**：新增实验域工具（如 `create_experiment`、`start_experiment`、`query_experiment_progress`、`query_experiment_result`），让"安排做一次 XX 实验"成为自然语言入口。

**现有前端 Tab 的定位（取舍）**：
- 现有 5 个 Tab（智能对话/文件管理/硬件设备/数据管理/网页填表）是"通用工具"面板，与实验主线正交，**保留为辅助工作台**，不并入实验三视角。
- 实验主线的三视角页面（看板/方案库+工作台/追溯）作为**新增页面**加入 Tab 框架，与现有面板并存。
- 硬件设备 Tab 是 M3 的"设备运维视图"；实验工作台是"实验执行视图"，二者不重复——前者看设备健康，后者看实验流程。现有 5 个 Mock 设备的展示数据在接入 MockDriver 后改为读取驱动层遥测，不再各自随机漂移。

**权限**：演示版角色切换开关（不做真权限）；生产版 RBAC 权限 + 审计联动。

### M6 数据采集与遥测

**职责**：实验过程中的数据点与设备遥测周期性入库。

- 演示版：Mock 采集器按实验剧本生成数据点（复用现有 `device_telemetry_history`，新增实验级 `measurements`）。
- 生产版：真实采集（串口/网络轮询或推送），断线补采、时间对齐。

### M7 审计与追溯

**职责**：回答"谁、何时、用哪台设备、对哪批样品/物料、按哪条方案、做了哪些操作、产出什么数据"。

- 复用现有 `tool_audits`，扩展实验域审计事件。
- 实验全链路记录：方案版本、人员、设备、物料消耗、步骤执行明细、数据点、异常记录。
- 增强：导出报告（符合实验室质量体系格式）。

## 5. 数据流（一条实验的一生）

```
[管理系统/Mock源] 方案下发 ──► M4 对接层 ──► 存入 M1.protocols
                                          │
实验员/Agent 发起 ──► M5 交互层 ──► M2 编排引擎 创建 M1.experiments
                                          │ 拆解步骤队列
                                          ▼
                                     M3 设备驱动（Mock/真实）
                                          │ 执行 + 遥测
                                          ▼
                                     M6 数据采集 ──► M1.measurements / telemetry
                                          │
                                          ▼
                                     实验完成/异常 ──► M7 追溯记录
                                          │
                                     M5 看板/详情展示，M4 回传管理系统
```

## 6. 关键设计原则

1. **引擎与设备解耦**：M2 只面向 M3 抽象接口，Mock/真实驱动可随时替换——演示版与生产版共用同一套编排逻辑。
2. **LLM 不进主链路**：实验执行是确定性的状态机；LLM 只做交互入口、文档解析、异常建议等"辅助决策"。
3. **演示版 = 生产版骨架的缩影**：演示版实现的每一层（数据模型、状态机、驱动抽象、API 形态）都是生产版设计的子集，不建"一次性演示代码"。
4. **追溯是核心价值**：任何数据写入都以"可关联回实验/设备/人员/物料"为前提。
5. **先数据后流程**：人机料关联的主数据模型先立，流程与页面都建在它之上。

## 8. 模块构建顺序（依赖关系）

以下为**构建依赖**而非时间排期——上层模块依赖下层的产物，只有按此顺序才能逐层打通：

```
M1 数据模型（人机料关联）
   │  依赖：现有 experiments/samples/devices 扩表 + 新增 protocols/materials/measurements
   ▼
M3 设备驱动抽象 + MockDriver 剧本引擎
   │  依赖：M1 的设备与测量定义；不依赖 M2（可独立先行验证驱动接口）
   ▼
M2 编排引擎（步骤展开 + 状态机 + 设备占用 + 异常冻结）
   │  依赖：M1 方案/步骤/实验结构 + M3 驱动接口
   ▼
M6 数据采集（实验级 measurements + 复用 telemetry）
   │  依赖：M2 执行过程中产出的数据点、M1 的 measurements 结构
   ▼
M5 交互层（三视角页面 + 实验域 Agent 工具）
   │  依赖：M2 的启动/进度/结果 API、M6 的数据曲线
   ▼
M7 审计追溯（全链路记录 + 查询）
   │  依赖：各层已写入的关联数据；可与 M5 并行补齐
   ▼
M4 管理系统对接（LIMS 适配器）
   │  长期才需要：演示版用预置方案（Mock 源）替代
```

- 演示版覆盖 M1→M7 的完整链路，M4 用 Mock 源占位。
- 生产版在演示版骨架上替换 M3 驱动与 M4 对接，其余模块不变。

## 9. 待决策事项

1. 演示主场景是否锁定"HTHP 失水仪实验"（有真实数据文件，领导认知度高）。
2. 角色/权限：演示版角色切换开关，生产版 RBAC——需确认演示对象（管理层）是否需要看到权限概念。
3. 目标 LIMS 系统的接口形态未知（REST / 文件 / DB），M4 适配器按可插拔设计，具体协议待接触后定。
